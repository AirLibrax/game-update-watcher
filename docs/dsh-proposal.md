# 游戏更新速报 v2 信息源重构：DSH 讨论方案

> 状态：讨论定稿（2026-08-25，实测验证后）
> 前置文档：`docs/design-v2-preview-sources.md`（本文是对它的回答与修正）
> 验证方式：本文所有 API 结论均通过 2026-08-25 实际请求官方公开接口核实（httpx，非猜测）

---

## 零、结论摘要（TL;DR）

1. **设计草案的「方案 1 / 方案 3」方向正确，但两个关键假设被实测否定**：
   - 米哈游 `getAnnList`（崩铁/绝区零）**不返回**前瞻直播总结公告与跃迁/调频卡池公告——无论 `type` 参数取什么值，都只返回单一「公告」组（崩铁 15 条 / 绝区零 20 条），`type_list` 里也只有这一个类型，`api-takumi` 域名已 404。**"从 getAnnList 解析下半池时间"不可行**，half_start 保持周期推算 + known_dates 兜底。
   - 鸣潮当前 `notice_url` 指向的 gamenotice 文件（16 条）**不含唤取卡池公告**，版本内容介绍里只有无标签的活动时间表（8/22、8/27、9/3、9/10、9/17 各段），无法可靠识别下半池。**"gamenotice 有跃迁公告"不可行**。
2. **方舟是本次修复收益最大的游戏，且数据完全支持自动修复**：`bulletinList` 里 cid=4841【墟】复刻即将开启（8/17 发布）的正文第一段就是 `活动时间：08月22日 04:00 - 09月05日 03:59`，与官网 news/7369 完全一致——**预告公告正文自带完整活动时间**，现有正则稍作映射即可提取，无需爬官网。
3. **终末地的"下版本时间"不在研发通讯里**：`「雪凇幽梦」版本研发通讯`（8/22，cid 4776）正文是纯优化项介绍，无更新时间、无新干员。官宣的 8/26 04:00 来自 B站官方动态（「理智补给」活动说明 `2026/08/26 04:00`、「深林覆雪」签到 `2026/08/26 12:00` 已实测），且正文日期是 **`YYYY/MM/DD` 斜杠格式**（现正则只认中文日期，需补规则）。
4. **B站动态源"可用但不稳定"**：实测方舟/终末地账号返回正常（方舟动态含"SideStory「墟」复刻即将于8月22日04:00开启！"），但鸣潮/崩铁账号从当前环境返回 `-352` 风控、绝区零返回空、终末地经 wbi 签名链路可能空返回。**结论：B站只做认证/补充源，永不当主源，失败必须静默降级**。
5. **新增一个实测发现的潜伏 bug**：版本制游戏在"新旧两期更新说明同时存在"时会产出**两个 GameUpdate → 汇总图同一游戏出现两块**（崩铁 8/26 后必然触发：4.4 与 4.5 更新说明同时在候选池）。必须加"主条目选择：取最新已开始版本"规则。

## 二、A. 信息源策略：逐游戏「下版本最早官方出处」

### 2.2 每款游戏的落地建议（针对用户问题的直接回答）

**终末地（hg_ssr）——"前瞻预告公告的结构、标题规律、能否稳定抽时间/干员"**

- 标题规律：`「版本名」+ 类型后缀`，三种后缀同构：`「X」版本更新说明` / `「X」版本研发通讯` / `「X」特许寻访说明`。→ **`「版本名」版本研发通讯` 的版本名可 100% 从标题正则 `「(?P<name>[^」]+)」版本研发通讯` 提取**，与现有 version_pattern 完全同构，实现成本极低。
- **不能**从研发通讯正文稳定抽更新时间/新干员（正文无这两个字段，实测）。
- 精确更新时间（8/26）当前只能来自：B站动态（③类，实测可得但要处理风控）或 8/26 当天的版本更新说明。**现实策略：研发通讯给 next_name + 触发"预告已发布"标记；更新时间维持周期推算并标注来源，B站/更新说明到位后自动替换**（信息增益从"未知版本名+预估时间"提升到"官方版本名+近准时间"，且永不显示错误值）。
- 若坚持要"无预估"：新增 slash 日期正则 `\d{4}/\d{2}/\d{2}` 从特许寻访说明/活动说明抓"版本更新维护前"前的具体日期（弱证据，仅作参考值），或等 8/26 更新说明。

**方舟（hg_json）——"bulletinList 里制作组通讯/活动预告的 cid 规律、正文时间格式"**

- **cid 无规律**（3358/4841/0400/1060 等，疑似随机/内部编号），不能按 cid 段分类；`category` 字段有弱规律（cat=1 游戏内容 / cat=2 官方通讯与声明 / cat=4 活动页），可作辅助。
- 可靠分类 = **标题后缀**：`「X」复刻即将开启`（预告）、`「制作组通讯」#N期`（路线图）、`「X」活动限时开启`（主活动）、`【X】限定寻访开启`（卡池）、`X限定寻访开启`（卡池）。
- 正文时间格式稳定：`活动时间：MM月DD日 HH:mm - MM月DD日 HH:mm` 为第一段首行（复刻/主活动/SideStory 三类公告实测均如此）；关卡分段用 `开放时间：`。现有 `活动时间/开放时间` 正则可直接命中 → **预告类公告的 `活动时间` 应映射到 `next_activity_start / next_activity_end`（当前代码只取了名字，漏了时间——这就是"墟只提取了名字没提取时间"的根因）**。
- 制作组通讯正文：`SideStory「名」限时活动将于X月上旬开启` → 名称正则可提，粗时间窗口**作为字符串展示**（"9月上旬"），不做日期解析。

**米哈游系（mihoyo_json）——"前瞻直播总结公告 ann_type、跃迁卡池公告解析 half_start"**

- 实测结论：**匿名 getAnnList 无法拿到这两类公告**（type 参数无效、pic 组为空、type_list 只有公告组）。ann_type 在此不可用。
- 因此：**不实现 half_start 的 getAnnList 解析**；half_start 维持 `start + half_days` 推算 + known_dates 兜底。更新说明正文里的第二组 `活动时间：` 存在但无"下半"标签且可能被联动提前（4.4 Fate UBW 7/24）——**不做启发式，避免错值**。
- 保持已验证正确的链路：更新说明 `end_time` → `next_update_time`（zzz 9/9、hsr 8/26 实测正确）。

**鸣潮（kuro_json）——"卡池公告（诸音声轨/唤取）标题与正文格式、half_start 提取"**

- 实测结论：当前 gamenotice 文件无唤取公告（标题规律无法从现有文件归纳，唤取公告在其它分类文件，hash 不可枚举）。
- 版本内容介绍的时间表无"上半/下半"标签 → **不做无标签启发式**（9/10 看着像下半池开始但无证据，写错比不写更糟）。
- half_start 维持推算；若用户强需求，后续探索方向：换 gamenotice 分类文件（需客户端抓包定位 hash）/ 库洛官网 API（SPA，需逆向 JS）/ B站唤取公告动态（风控不稳定）。**列入 P2，不做承诺**。

## 三、B. 字段抽取健壮性：正则覆盖率实测 + LLM 混合策略

### 3.1 正则覆盖率实测估计（以 8/25 全部可达源为样本）

| 字段 | 方舟 | 终末地 | 崩铁 | 绝区零 | 鸣潮 | 缺口性质 |
|---|---|---|---|---|---|---|
| update_time（本版本开始） | 100%（活动时间行） | 100%*（列表日期=更新日） | 100%（adapter start_time） | 100%（同左） | 100%（维护时间，中文日期） | 无 |
| activity_end（活动结束） | 100%（关卡/活动时间行） | — | — | — | — | 无 |
| next_update_time（下版本时间） | 预告类 100% 可补（正文活动时间） | 0%（研发通讯无；B站 slash 格式需补正则） | 100%（end_time） | 100%（end_time） | 0%（文件无） | **字段在源里不存在（终末地/鸣潮）** |
| next_name（下版本名） | 100%（预告标题/制作组通讯） | 100%（研发通讯标题） | 0%（源不可达）→ known_dates | 0%（同左） | 0%（同左） | 源不可达 |
| characters（新角色） | 100%（★行） | 100%（更新说明「全新干员」段） | 100%（更新说明） | 100%（更新说明） | 100%（版本内容介绍） | 无 |
| half_start（下半池） | —（无上下池概念） | 0%（特许寻访时间=当期寻访开始，语义不符） | 0%（卡池公告不可达） | 0%（同左） | 0%（唤取公告不可达） | **源不可达** |
| preview_time（前瞻直播） | 不适用 | 0%（news 无条目）→ known_dates | 0%（不可达）→ known_dates | 0%（同左） | 0%（同左） | 源不可达 |

\* 终末地注意：hg_ssr 的 update_time 是**列表页日期**（=发布日）；对"版本更新说明"类条目发布日=更新日，对"研发通讯"类条目发布日≠版本开始日 → 预告类条目**不得**进入主条目的 update_time 计算（否则节奏锚点错位）。

**整体结论**：在"可达源"内，纯正则对核心字段的覆盖率约 **70~80%**；剩下的缺口约 40% 是"字段根本不在可达源里"（LLM 也无能为力，只能换源或 known_dates），约 20% 是格式差异（终末地 slash 日期、`<t>` 标签包裹、B站动态文本），约 10% 是语义歧义（活动时间表里哪个是下半池、制作组通讯的"9月上旬"）。**投入产出比最高的动作是补 slash 正则 + 预告类字段映射（代码量 < 100 行），而不是上 LLM**。

### 3.2 LLM 辅助抽取（ctx.llm）的权衡与混合策略

**权衡**：
- 延迟：一次 LLM 调用 2~10s。定时轮询（6h）无感；但 Tool/指令按需触发时用户多等数秒——**必须只在"正则失败且文本有信息"时触发**（正常路径 0 次调用）。
- 成本：每轮每游戏 ≤1 次，每天总量 < 20 次，可忽略。
- 可测试性：LLM 输出必须走**结构化 schema + 断言校验**，且仍作为 claim 注入现有 aggregate 通道（不绕过置信度体系），可用 golden corpus 回归 + mock。

**混合策略（推荐）**：
1. **正则层（默认）**：现有规则 + 新增 slash 日期正则 + 预告类字段映射。确定性、可单测、零延迟。
2. **LLM 层（仅失败路径）**：触发条件 = 公告属预告类（研发通讯/制作组通讯/前瞻总结/活动预告）且目标字段正则未命中且文本含时间线索（`X月X日|X月上旬|YYYY/MM/DD`）。
3. **输出契约**：`{"next_update_time": "2026-08-26", "next_name": "雪凇幽梦", "characters": ["提弗洛斯"], "rough_window": "9月上旬", "evidence": "原文片段"}`；**断言**：日期可解析、位于未来 60 天内、与周期推算偏差 ≤14 天，否则丢弃。
4. **权重**：LLM claim weight ≤ 0.8（低于官方公告解析的 1.0），保证"弱源不覆盖强源"；多源一致才提升置信度。
5. **来源标注**：任何非官方公告解析值（含 LLM 值）在图上标注来源类型（如"官方预告"/"周期推算"），预估标记逻辑不变。

## 四、C. 方舟事件列表状态机设计

### 4.1 数据模型

```
Event {
  name: str            # 活动名（SideStory/复刻/联动名）
  kind: main|reprint|banner|roadmap   # 来源分类
  start: date|None     # 活动开始（预告类取自正文"活动时间"）
  end: date|None       # 活动结束（关卡期；无则 displayTime+cycle 兜底并标预估）
  announced_at: date   # 公告发布日（displayTime）
  source_cid: str      # 溯源
}
status(event, today) = upcoming | active | ended
  active   = start <= today <= end
  ended    = today > end
  upcoming = today < start
```

事件来源映射（build_updates 重构后）：
| 公告标题特征 | kind | 产出字段 |
|---|---|---|
| `「X」活动限时开启` / 含 SideStory 开启段 | main | name, start, end（活动时间行） |
| `【X】复刻即将开启` / 复刻预告 | reprint | name, start, end（**新增：正文活动时间 → next_activity_start/end**） |
| `【X】限定寻访开启` / `X限定寻访开启` | banner | name, banner_start/end（正文空则跳过，如 cid=1060） |
| `「制作组通讯」#N期` | roadmap | 通讯节点：`SideStory「名」…将于X月上旬开启` → (name, rough_window 字符串)，不解析为日期 |
| 历史旧公告（end < today） | — | 保留在事件列表但不进栏位 |

### 4.2 状态机规则（解决本次 bug 的核心）

1. **结束判定 = 解析出的活动 end（关卡时间），不用"出现新公告"推断**（bulletinList 不清历史，酸橙 8/22 结束但公告仍在列表 → 旧逻辑靠优先级选主导致酸橙占位；新逻辑按 `active` 过滤直接淘汰）。
2. **多活动并行**（实测存在：嘉年华商店期 8/22~8/29 与墟 8/22~9/5 重叠）：事件列表同时保留多个 active，栏位选择时取 **start 最新的 active 作栏位 A**，其余 active 作栏位 B。
3. **预告升格**：`【墟】复刻即将开启` 解析出 start=8/22 ≤ today → 自动从"下版本预告"升格为 active 主事件——**这就是"墟只提取了名字没提取时间"的完整修复**（时间提取 + 升格两条腿）。
4. **空窗期**：无 active 事件时，栏位 A = 最近的 upcoming 事件（标"即将开启"+ 官方时间或预估），栏位 B = roadmap 最近节点；完全无预告则 A="暂无活动，等待官方公告"（note 说明），**绝不显示已结束活动冒充当前**。
5. **roadmap 展示**：制作组通讯给的 next-next（如月行水上 9月上旬）作为栏位 C 或 B 的"官方预告"行——日期用原始字符串（"9月上旬"），不假装精确。

### 4.3 对 timeline.py 的影响

- `_activity_timeline(update, cfg, start, today)` 改为 `build_activity_timeline(events, today)`：入参从"单 GameUpdate"变为"事件列表"，栏位生成逻辑改为状态机选择。
- 栏位结构（8/25 视角的期望输出）：
  - A = 「墟」复刻 `8月22日 ~ 9月5日`（官方值，无"预估"）＋ 复刻干员（若有）
  - B = 「月行水上」联动 `9月上旬（官方预告）`（来自制作组通讯#68，日期为粗窗口字符串）
  - C（可选）= 中坚甄选 进行中（正文空则省略该栏）
- `TimelineSlot` 增加可选 `rough: bool`（日期为字符串窗口时用，不走 parse_date/预估色逻辑），或复用 estimated 标记 + 文案区分。
- 渲染层**无需改动**：renderer 的区块高度按 `len(slots)` 自适应（formats/*.json 模板与槽位数量解耦，已确认）。
- pipeline.py 的 activity_mode 合并逻辑（`updates.sort(key=_priority)` 那段）整体替换为事件列表构建；`next_activity/next_is_reprint` 字段并入事件模型。
