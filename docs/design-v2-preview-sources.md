# 游戏更新速报 v2 设计提案：下版本信息采集重构

> 状态：草案（待与 DSH 讨论）
> 日期：2026-08-25
> 背景：8/25 实测发现汇总图大半数据与现实不符，根因不是参数问题，而是**信息源结构缺口**

---

## 一、现状架构（v0.1）

```
采集层 Adapter → 解析层 字段提取 → 认证层 交叉认证 → 节奏层 timeline → 渲染 Pillow
```

- **主源**：各游戏官方公告接口，`games/*.json` 的 `title_include` 匹配"版本更新说明/更新公告"类标题，选出一个**主条目**（当前版本）
- **认证源**：B站官方账号动态（bili_dynamic），对主条目字段做加权校验
- **节奏推算**：主条目的 `update_time + cycle_days` 推算下版本；官方 `end_time` / `known_dates` 覆盖
- **核心假设**：一个游戏同一时刻只有一个"主条目"，下版本信息从主条目字段或周期推算得来

## 三、根因分析（三个结构性缺口）

### 缺口 A：「预告类公告」不在采集范围

下版本信息的官方载体是**前瞻预告 / 制作组通讯 / 版本PV / 研发通讯**，而不是版本更新说明：

- 终末地：官网 news 列表有「雪凇幽梦」版本前瞻预告（含更新时间、新干员）
- 米哈游系：前瞻直播总结公告、版本预告页
- 方舟：制作组通讯 #68 期（verify 已命中此公告！但只用于认证没解析 next_*）

当前 `title_include` 只匹配"版本更新说明"，预告类公告要么不进候选池，要么进了但只当认证源。

### 缺口 B：正文时间提取不完整

方舟复刻公告正文第一段就是"活动时间：08月22日04:00 - 09月05日03:59"，但解析器没有把这类**未来活动的开启时间**映射到 `next_activity_start` 字段——只提取了活动名。

### 缺口 C：活动制游戏缺"多活动时间线"模型

方舟同一时刻并行存在：主线活动（已结束）、复刻活动（进行中）、寻访卡池、下一个活动预告。"单主条目 + 两三栏位"模型表达不了这种状态机：

```
活动A(8/1~8/22)[结束] → 活动B=复刻墟(8/22~9/5)[进行中] → 活动C[预告中]
```

当前逻辑：主条目=A，A 过期后仍占位；B 只能作为"A 的下版本预告"存在，无法升格为主条目。

## 四、改进方案草案

### 方案 1：引入「第二遍扫描：预告类公告 → next_* 字段」（解决 A、B）

- `games/*.json` 新增配置块：
```json
{
  "preview_sources": {
    "title_include": ["前瞻预告", "制作组通讯", "研发通讯", "版本PV", "活动预告"],
    "field_map": {
      "next_name": "「(?P<name>...)」",
      "next_update_time": "更新.*(\\d+月\\d+日)",
      "next_characters": "全新干员/角色段落"
    }
  }
}
```
- pipeline 第二遍：候选池里命中 preview_sources 的公告 → 提取 next_* 字段 → 注入主条目 claim（置信度按公告类型定权）
- 效果：终末地下版本直接显示官宣值；方舟墟的 8/22 从正文提取

### 方案 2：活动制游戏改「事件列表」模型（解决 C）

- 方舟不再选唯一主条目，而是产出**事件列表**：每个候选活动 → (名称, 开始, 结束, 状态)
- timeline 按 today 过滤：进行中的活动做栏位A，最近的预告做栏位B/C
- 已结束且无接替的活动才回退到"空窗期"展示

### 方案 3：卡池公告解析 half_start（补漏）

- 米哈游 getAnnList 的"跃迁/寻访"类公告、鸣潮 gamenotice 的卡池公告 → 解析上半/下半池角色与时间 → 官方 half_start 覆盖推算值
- 实测案例：绝区零 3.1 下半池「蕾米埃尔&希格莉德」跃迁公告已在 getAnnList 中，正文含官方时间，当前未被解析

### 方案 4：预估标记加时间维度（修复自相矛盾）

- 现状：`estimated = 没有官方数据源`，与日期是否已过去无关 → 出现「8/19 开启(预估)」而今天已 8/25 的荒谬显示
- 规则：推算日期 <= today 时去掉预估标记（日期已兑现即事实）；未来日期才保留预估标注
- 这是 timeline.py 的纯展示层修改，风险最低，可先行落地

### 不做的事

- 不引入第三方 wiki/爬虫源（稳定性差、合规风险），坚持官方接口 + B站官号
- 不做实时推送频率提升（6h 轮询足够，公告延迟不是瓶颈）

## 五、待与 DSH 讨论的问题

1. **信息获取优先级**：五款游戏各自的"下版本信息最早官方出处"是什么？（终末地=官网前瞻预告新闻页？米哈游=前瞻直播总结公告？方舟=制作组通讯？）各源的发布时序与可靠性排序
2. **预告类公告的字段抽取健壮性**：前瞻预告正文的排版差异大（有的时间是图片而非文字），纯文本正则的覆盖率估计多少？要不要引入 LLM 辅助抽取（插件内有 ctx.llm 能力可用）？
3. **活动制事件列表模型**：状态机怎么设计（结束判定用 activity_end 还是"出现更新的活动"）？空窗期怎么展示？
4. **known_dates 的角色**：改造后 known_dates 是否退化为兜底（仅当自动提取失败时手工兜底）？

## 六、MaiBot 插件规范约束（实现时必须遵守）

以下均为本次排查中从源码/官方文档确认的硬性约束：

1. **config_model 结构**：必须嵌套 `[plugin]` 节；PluginSection 必须显式声明 `enabled` 与 `config_version` 字段（Runner 从 build_default_config() 提取 config_version 做校验，缺失即拒绝加载）
2. **能力声明精确匹配**：manifest capabilities 必须写完整能力名（如 `send.image`、`chat.open_session`），Host 是精确字符串匹配，无前缀推导
3. **顶层包名禁止 core**：MaiBot 自身 src/core 已占用 sys.modules，插件内部包需用独特名（现 guw_core）
4. **配置来源**：运行时配置 = 插件目录 config.toml（Runner 维护）；插件内读自身配置用 `get_plugin_config_data()`（本地方法不经 RPC，无 E_CAPABILITY_DENIED 风险）
5. **生命周期**：on_load/on_unload/on_config_update 三方法必须实现，否则 Runner 拒绝加载
6. **路径**：持久化用 ctx.paths.data_dir，临时产物用 runtime_dir，不要自拼路径
7. Python >= 3.10（部署环境 3.12 有 tomllib；插件自带 configparser 回退兼容 3.10）
